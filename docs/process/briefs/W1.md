# W1 brief: Keeper engine

You are building the Keeper engine for Clean Sheet, an oversight layer that watches a solo founder's AI worker agents. Read `docs/battleplan.html` sections 03 and 05 for context, then `fixtures/starter-kit/` (AvePoint's kit: `README.md`, `rules/*.md`, `rules/*.json`, `data/`) and `fixtures/extra/` (our S6, S7 and rules R20 to R22).

## Goal

A deterministic engine that decides on every worker-agent read and action: ALLOW, HOLD_FOR_APPROVAL or BLOCK, with the rules that fired, the evidence, the data level and a plain-language owner message. Done means `npm test` passes and `node scripts/score.js` prints 15/15 on kit scenarios S1 to S5, 6/6 on S6 and S7, and every normal action correct.

## Hard rules

- Plain JavaScript ES modules, Node 24, **no npm dependencies**. Tests use `node:test`. `package.json` with `"type": "module"` and scripts `test` and `score`.
- **Code decides.** No LLM calls anywhere. Owner messages come from templates filled with evidence.
- **No special-casing.** Never branch on scenario IDs or hard-code file names or figures from the kit in engine code. Everything comes from the policy JSON, the taxonomy JSON, file headers, file contents, the client and supplier lists, and the task description. The scenario harness may declare each task's instruction and scope, because in production the orchestrator states the task.
- Keep the core portable: modules under `src/keeper/` take plain objects (files as `{path, header, body}`), never touch the file system. Only `src/fixtures.js` and `scripts/` read files. Hashing may use `node:crypto` in its own module only.
- **Do not modify anything under `fixtures/starter-kit/`.** You may add test data under `fixtures/extra/` and `tests/`.
- Do not run git commands. Do not commit. Do not install anything.

## What to build

1. `src/fixtures.js`: load kit `data/` overlaid with `fixtures/extra/data/`, parse front-matter headers (`sensitivity`, `trust`, `from`, `to`, `date`, `title`), load policy, taxonomy, scenarios and extra scenarios.
2. `src/keeper/labels.js`: label a file (header first, confirmed by the taxonomy's detection hints; `client_list.csv` has no header and takes its README's label) and label outgoing text. **The kit's identifiers are deliberately invalid**, so NRIC, card and bank checks match the pattern only (NRIC: letter, 7 digits, letter), no checksums. Implement R22: an outgoing draft's level is the highest of its own content, its attachments and every file the agent read in the task. Also record which client each confidential item belongs to (from header, title, file name or contents).
3. `src/keeper/policy.js`: match an action against R01 to R19 plus R20, R21. Collect **every** matching rule; the strictest wins (NEVER → BLOCK, APPROVE → HOLD_FOR_APPROVAL, ALLOW → ALLOW); cite all of them. Parties come from `admin/client_list.csv` and `admin/supplier_list.md`. Owner floors from `policy.json`. R21: recipient or instruction that appears only in inbound text marked `trust: untrusted` or from an unknown sender, not on the client or supplier list, or a lookalike of a known client domain (edit distance or shared brand token).
4. `src/keeper/figures.js` (R18): extract every amount, percentage, duration (including words like "two days") and date from outgoing text. Each must match a figure in a file tied to the same client or task. If not, flag it with the closest figure of the same kind and its source file, side by side. A figure with no source is never ALLOW.
5. `src/keeper/scope.js` (R01, R02): reads outside the declared task scope are logged as scope creep; a regulated file read outside scope fires R02.
6. `src/keeper/engine.js`: `decideRead(task, file)`, `decideAction(task, action)` and `runTask(task, steps)` returning events shaped like the contract below. A task's scored outcome: decision of its outgoing action (or of the strictest read if it has none); rules = all rules fired across the task.
7. `src/keeper/log.js`: append-only audit log, each row carries `seq`, `hash`, `prev_hash` (SHA-256 of the previous row). Include a `verify()`.
8. `src/keeper/messages.js`: owner messages in the kit's style. Short, plain words, the money at stake, what the owner can do. See each scenario's `owner_message` for the target tone.
9. `scripts/score.js`: run S1 to S7 through `runTask` using a harness file `tests/harness.json` that you write (per scenario: task instruction, agent, declared scope, and the steps as structured tool calls taken from `worker_agent_does`). Score the kit's way: 3 points per scenario (right decision; every expected rule cited; evidence cited, meaning each file path and key figure named in the expected evidence appears in our evidence). Print a table and totals. Also list extra rules we cited beyond the expected ones as warnings.
10. `tests/normal_actions.json` + test: at least 30 normal actions across all agents, each with the decision the policy says is correct. Include deleting `inbox/2026-11-13_nimbus_patient_data_in_error.md` per the Nimbus contract (R17: ALLOW, plus notify client and owner), sending the public Harbourbean case study to Greenstep (ALLOW), quoting within the price list (ALLOW), a payment reminder to an existing client (ALLOW), and replies whose figures all trace to files (ALLOW). Zero false alarms.
11. Unit tests for labels (score all 28 files against `rules/ground_truth_labels.json`, must be 28/28), figures, policy precedence and log verification.

## Event contract (match these shapes)

```json
{"type":"file.read","task_id":"...","agent":"...","file":"...","level":"regulated","in_scope":false,"decision":"BLOCK","rules":["R02"]}
{"type":"action.proposed","id":"...","task_id":"...","agent":"...","tool":"send_email","args":{},"level":"client-confidential","inherited_from":["clients/..."]}
{"type":"keeper.decision","id":"...","decision":"BLOCK","rules":["R18","R09"],"data_level":"client-confidential","evidence":[{"claim":"25%","source":"clients/contract_ferro_logistics_2026.md","value":"20%","text":"..."}],"owner_message":"..."}
```

Tools to support: `read_file`, `send_email` (to, body, attachments), `quote_price`, `accept_terms`, `pay_supplier`, `order_from_supplier`, `upload_to_external_tool`, `delete_file`.

## When done

Write `result.md` in the repo root: the score output pasted in full, `npm test` summary, a list of files you made, every judgement call you made about ambiguous kit rules (for example why S4 cites R09, or how scope is declared), and known gaps. Keep it under 120 lines.
